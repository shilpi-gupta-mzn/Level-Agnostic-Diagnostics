# Reproducibility Artifacts for Level-Agnostic Diagnostics

This repository accompanies the paper:

> **From Ontological Violations to Explicit Witnesses: Level-Agnostic Diagnostics for OntoUML and MLT**

It provides the model, profile, core, program, and result artifacts needed to inspect and reproduce the paper's diagnostic example.

## Artifact kinds

The repository contains five kinds of artifact:

1. **Model** — the facts and structures that constitute the `Violation_Seeded_Model` used as the running example in the paper.
2. **Profiles** — the predefined vocabulary and rules from LML, MLT, and OntoUML that are relevant to the example.
3. **Core** — the predefined PAMoLa vocabulary and core rules required by the example.
4. **Results** — the expected outputs generated by executing the integrated program.
5. **Integrated program** — a self-contained combination of the model facts, required core and profile content, and case-specific diagnostic rules.

## Representation forms

The artifacts are exposed in two complementary source representations, with generated results supplied in a third form:

- **PAMoLa HUTN (`.hutn`)** — Human-Usable Textual Notation for the structural PAMoLa representation. It makes carrier kinds, custody, nesting, references, profile content, and reified rules explicit.
- **Datalog (`.dl`)** — a conventional fact-and-rule view of the corresponding content. The concrete syntax used in this repository is accepted by Nemo and can also be inspected independently of the PAMoLa implementation.
- **CSV (`.csv`)** — the tabular form of the expected and generated program outputs.

For every artifact supplied in both forms, `<name>.hutn` and `<name>.dl` describe the same intended content from different perspectives. The HUTN file is the structural PAMoLa view; the Datalog file is its relational fact-and-rule view. The two files are therefore semantically aligned, although their textual organization is necessarily different.

## The violation-seeded model

`Violation_Seeded_Model.hutn` is the structural representation of the model shown in the paper. It includes higher-order classifiers, first-order types, ordinary individuals, the `worksFor` relationship, OntoUML interpretations, and MLT powertype, categorizer, and partition relations.

`Violation_Seeded_Model.dl` contains the corresponding model fact view. It is not a separately authored model: it is the relational projection of the HUTN content used by the rule program.

## Profiles

The repository contains three profiles. Here, **relevant** means the vocabulary and rules needed to represent and execute the example in the paper. The profile artifacts are reproducibility artifacts, not complete specifications of every construct supported by the corresponding languages or tools.

### LML

LML (Level-Agnostic Modeling Language) supplies the classification and potency vocabulary and well-formedness rules used to organize the model across ontological levels. LML was originally developed in the potency-based multi-level modeling tradition associated with MELANEE.

Potency is used directly in this example: the non-adjacent-classification diagnostic detects that `Taylor`, with potency zero, is directly classified by `PersonTypeByGender`, with potency two, rather than by a classifier one potency step above it.

### MLT

The MLT profile supplies the referenceable vocabulary used for higher-order concepts such as `powertypeOf`, `categorizes`, and `partitions`. No separate MLT-specific rule set is required for the examples studied in the paper; the operational interpretation needed by the diagnostics is included in the case-specific part of `Program.dl`.

### OntoUML

The OntoUML profile supplies the referenceable stereotype vocabulary and stereotype-family information used by the example. The case-specific Kind and BinOver rules are included in `Program.dl`.

The profile files should not be read as a complete executable formalization of the entire OntoUML specification or anti-pattern catalogue. They contain the OntoUML profile content needed for this reproduction.

## PAMoLa core

`PAMoLa_Core.hutn` exposes the relevant core categories, properties, datatypes, and reified rules as PAMoLa content. `PAMoLa_Core.dl` presents the corresponding facts and rules in ordinary Datalog notation.

The core provides the common structural vocabulary used by the model and profiles, including entities, relationships, participations, categorizations, intercalations, markers, custody, typing, and the generic rule representation.

## The integrated `Program.dl`

`Program.dl` is supplied so that readers can inspect or execute the complete paper scenario without assembling the individual files themselves. It combines:

1. the complete fact view of `Violation_Seeded_Model`;
2. the required rules from the PAMoLa core;
3. the required rules from the LML profile;
4. the required OntoUML profile-family facts; and
5. the case-specific semantic and diagnostic rules used in the paper.

The file is specific to the paper's running model. It contains the rules needed to reproduce the reported results, not a general-purpose validator for arbitrary PAMoLa, LML, MLT, or OntoUML models. The separate HUTN and Datalog files are provided so that readers can trace each part of the integrated program back to its structural source.

The program's export directives produce CSV files for the diagnostic predicates. The generated files should be compared with the corresponding expected files in `results/`.

## Interpreting the results

The CSV files in `results/` represent the expected raw outputs of the integrated program. Each row is a diagnostic witness containing the model references, profile terms, reason terms, or scalar values returned by the corresponding rule.

The paper may present these raw outputs in a normalized, modeler-facing form—for example, by showing an unordered pair only once or preferring a more specific diagnostic over a general one. Such presentation decisions do not remove or change the raw facts produced by the program.

## Traceability and modification

The paired files are supplied for inspection and traceability:

- use the `.hutn` files to inspect the structural PAMoLa content;
- use the `.dl` files to inspect the corresponding facts and rules;
- use `Program.dl` to reproduce the complete example; and
- use `results/` to compare the generated outputs with the expected results.

When modifying an artifact, its paired representation and any affected integrated-program or result files should be regenerated rather than edited independently. This is particularly important for absence-sensitive rules: omitting a fact can change the diagnostic closure rather than merely changing the presentation.
